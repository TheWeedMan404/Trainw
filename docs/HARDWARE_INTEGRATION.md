# TRAINW Hardware Integration

## Endpoint

- URL: `https://<your-project>.supabase.co/functions/v1/gate-checkin`
- Method: `POST`
- Headers:
  - `Content-Type: application/json`
  - `apikey: <SUPABASE_ANON_KEY>` for browser kiosk calls
  - `Authorization: Bearer <token>` is optional for the gate terminal flow

## Common Response

Every request returns JSON with the same top-level contract:

```json
{
  "access": true,
  "client_name": "Sana Ben Ali",
  "days_left": 12
}
```

Denied example:

```json
{
  "access": false,
  "reason": "membership_expired"
}
```

The hardware controller only needs to check `access`.

## Payloads

### QR

The QR `token` is a single opaque 128-bit crypto-random string (32 hex
characters). It carries no user id, gym id, or timestamp — the member and
gym come from the `gate_sessions` row the token points to, and the
legacy dotted format (`userId.gymId.timestamp.random`) is rejected by
the handler. Tokens live 60 seconds and are single-use.

```json
{
  "type": "qr",
  "gym_id": "GYM_UUID",
  "device_id": "gate-1",
  "token": "9f2c4a7e1b83d05f6a24c9e0b817d3a5"
}
```

### RFID Card

```json
{
  "type": "rfid_card",
  "gym_id": "GYM_UUID",
  "device_id": "gate-1",
  "credential_data": "04A2248B91"
}
```

### Fingerprint

```json
{
  "type": "fingerprint",
  "gym_id": "GYM_UUID",
  "device_id": "gate-1",
  "credential_data": "FP-TEMPLATE-0142"
}
```

### Face

```json
{
  "type": "face",
  "gym_id": "GYM_UUID",
  "device_id": "gate-1",
  "credential_data": "FACE-PROFILE-7781"
}
```

## Enrollment Flow

1. Register the member on the hardware first.
2. Copy the hardware UID or template ID into TRAINW from the `Badges & Biométrie` tab.

## Notes

- `credential_data` is only the hardware identifier.
- Actual biometric image or template data is never sent to Supabase.
- Every access attempt is written to `gate_access_log`.
- Successful hardware validations also create a `check_ins` row for attendance.
- **Rate limiting is the lockout control (DB-48).** There is no
  per-credential lockout inside `validate_member_credential` — the
  throttle lives in the `gate-checkin` edge function instead, before
  any token/credential lookup: 60 requests/minute per IP and 30/minute
  per device (`trainw_gate_rate_limit_consume`, migration
  `20261114040000`). A refused attempt does not inflate the counter.
  Verified behaviourally on a local cluster (30 device calls allowed,
  31st refused, buckets independent). If the limits ever need tuning,
  change them in `handler.mjs` (`RATE_LIMITS`), not in the RPC — the
  RPC takes the limit as a parameter.
- **Client codes are display-only (NX-29).** The member code (`GYM-042-K`
  format, generated by the archived schema's `generate_unique_client_code`)
  is a short, low-entropy, format-predictable identifier shown in the
  dashboard and returned on public registration. It must **never** be
  accepted as proof of identity by any check-in or gate flow: the gate
  accepts only single-use QR tokens and enrolled hardware credentials
  (RFID/fingerprint/face) validated by `validate_member_credential`. No
  code path in `gate-checkin`, `gate-terminal.js`, or the gym dashboard
  reads a client code as a credential — keep it that way. If a code is
  ever needed as a credential, lengthen it to 8+ random alphanumeric
  characters and rate-limit its verification first.
